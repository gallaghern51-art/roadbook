# CLAUDE.md

**Roadbook** — multi-trip AI motorcycle trip planning platform (React SPA + Netlify Functions). Born as the Sturgis 2026 field-guide app; the Sturgis trip now lives on as seed data / template. Live at https://roadbook-app.netlify.app. Repo: `gallaghern51-art/roadbook`.

## Commands

```bash
npm run dev      # Vite dev server on port 5199
npm run build    # production build → dist/
```

There is no test suite or linter configured. Verify changes by building and exercising the UI; the engine functions in `src/engine/` are pure and easy to check in isolation.

## Deploys

Pushes to `main` auto-deploy via Netlify CI (site `roadbook-app`, team GalCode — `roadbook` was already taken on netlify.app). `npx netlify deploy --prod --dir dist --functions netlify/functions` still works as a manual fallback. `ANTHROPIC_API_KEY` is set in the Netlify site env — functions read it at deploy time.

**Others also work on this repo via GitHub PRs. Always `git pull --rebase` before pushing, and read what came in — remote work has restructured whole subsystems before.**

## Architecture

State flows one way: **every trip mutation is an op** (`src/engine/ops.js`) applied by the pure `applyOps(trip, ops)`; the reducer in `src/engine/store.js` persists to localStorage and maintains undo. The UI and the AI optimizer emit the *same op vocabulary* — if you add an editing capability, add it as an op, wire it into `describeOps`, and expose it in the function's tool schema so the AI can use it too.

- `src/engine/store.js` — trip library (`moto.trips.v1` in localStorage): multiple trips, per-trip scenarios, active-trip working copy, undo stack.
- `src/engine/tripEngine.js` — miles/hours/fuel-gap warnings. Bike range comes from `trip.meta.range` (`tripRange()`), never hardcode 180/200.
- `src/engine/timeline.js` — minute-by-minute day simulation (depart → routed leg minutes → dwell → ETAs), hard-gate checks (`day.gates`), feasibility scores/grades.
- `src/engine/dates.js` — `cascadeDates(trip)` re-pins every `day.date/dow` from `meta.startDate` + index. Call it after any day add/remove/reorder or startDate change (ops already do).
- `src/engine/routing.js` — **Valhalla motorcycle owns planning, Ride Mode, and live reroutes** (Sept 6–7, 2026). Planning falls back directly to OSRM; Ride directions and live reroutes fall back through Google Routes → OSRM. Google is traffic-aware through `netlify/functions/google-route.mjs`, and OSRM is the final safety net plus best-effort route-ref/lane enrichment through `attachRoadDetail`. `routeDay` uses `break_through` for intermediate stops (separate legs without waypoint U-turns), decodes polyline6 geometry, and caches by route preference + the day's coordinate string in `sturgis.routeCache.v5`. `trip.meta.routePrefs` is the op-backed, shared trip choice: `style` is `quick|touring|backroads`, translated to Valhalla motorcycle `use_highways` 1/0.5/0.05; `avoidTolls` sets `use_tolls` to 0; `use_trails` is always 0 until unpaved routing gets explicit safety UX. The Trip settings control owns this input, and the same value flows through plan geometry, cached Ride maneuvers, and live reroutes. **After a trip exists, this is a protected replan rather than an instant toggle:** a click routes every day into a draft without mutating shared state, overlays the proposed geometry, compares mileage/time/feasibility and new warnings, locks booked lodging + timed commitments, then offers Cancel, Keep every stop, or Find better-fit stops. Keep is one undoable `set_meta` op after explicit confirmation. Find hands the constraint inventory to Copilot; it holds booked lodging, overnight cities and gates, preserves the role of flexible places, and only proposes an atomic change after the rider chooses replacements. The server carries the Valhalla corridor into Google Places Search Along Route, requires a second Valhalla evaluation, persists matching proof into the next chat turn, and rejects any route-preference proposal without that proof; it also rejects reconciliation ops that touch booked lodging, endpoints, hard gates, or completed reservations. Both draft and active-plan routing are latest-only through independent AbortControllers and three-worker pools, and the active route set swaps atomically—never one day at a time—so geometry cannot lag one click or mix route characters. Aborting a request never trips Valhalla's outage backoff. Each input pin is projected onto the Valhalla shape so DayPanel retains its >150 m off-road warning. A successful Valhalla plan is cached until coordinates or route preferences move; an OSRM planning fallback lasts only through Valhalla's 10–30 minute backoff. Navigation steps use `moto.stepsCache.v6`. Valhalla lengths are miles and times need no `SPEED_CURVE` calibration; only OSRM fallback durations are calibrated. Cached legs and steps are UNPACED: `trip.meta.pace` is applied at read time. Do not add `continue_straight=false` or `snapping=any` to OSRM requests; that previously allowed mid-pass U-turns. Legs use `legKey(a, b)`, so moving a waypoint invalidates naturally. Verified by `route-preview-check.mjs`, `valhalla-check.mjs` (draft/cancel/commit plus authoritative-path/control behavior), and the 15/15 Ride Mode forced-fallback sim.
- `src/components/TripConstructionChat.jsx` + `netlify/lib/route-opportunities.mjs` — **AI-native construction owns the front door** (Sept 6–7, 2026). New Trip is a full-screen, two-stage pre-commit conversation and route workbench, not a one-shot generation field or modal. The initial name/date/days/riders frame gets its own intake region; after the first planning turn it collapses to a compact, editable context strip so route decisions own the viewport. On desktop the active builder is a side split: independently scrolling conversation/refinement on the left and selected route/stops/confirmation on the right. On a phone those become `Conversation` and `Route plan` panes instead of an upper/lower split; new options open the plan automatically and a stop's `Change` action returns to the conversation with the refinement prompt prepared. The AI component stays mounted when the rider visits Blank or Template, preserving the conversation, options, selection, refinement draft, and progress on return. `runExplore` gives the model live Google Places search, Valhalla evaluation, and structured option presentation; it cannot generate a trip. Follow-ups are patches: for additive requests, a server-side shortest-common-supersequence merge restores any prior locations an abbreviated model response omitted before Valhalla measures the result, so adding a Day 1 meal cannot silently delete Day 2. The prior 12-location whole-trip slice is gone; concepts accept up to Valhalla's default 20 locations and over-limit options fail visibly instead of losing the tail. The server fact boundary measures up to three motorcycle bundles with `break_through` stops, group-paced riding time, dwell/arrival, fuel gap vs range, detour delta, and best-effort `/height` ascent. Fuel/food/lodging candidates that arrive without a Places id are resolved again server-side before routing; verified and unverified businesses are visibly distinct, so live identity is enforced rather than trusted to the prompt. Verified food, lodging, and attraction rows expand to live rating/count, price, address, weekly hours, phone, website, and Google Maps links with visible Google attribution; those Places facts remain ephemeral. The UI joins trusted facts to AI-authored why/group-fit/tradeoff prose. Riders can replace any intermediate stop, keep roads/change stops, keep stops/change roads, or shorten an option; each refinement is researched and routed again. Only a selected option plus explicit Create this trip confirmation enters `runGenerate`. `VALHALLA_URL` overrides the public prototype endpoint. DayPanel's “Find route opportunities” opens the same search→evaluate intelligence in Copilot without immediately proposing ops. Verify with `npm run opportunities:check`, `npm run preferences:check`, `npm run builder-progress:check`, and `construction-chat-check.mjs` (25/25). The rider's route preferences (`Roads` style + `Avoid tolls`) are set in the builder frame, ride into every evaluation, and are written onto the created trip — a model that omits `routePrefs` from its tool call is backfilled from `basics` rather than measured under the evaluator's defaults.
- `src/engine/speedLimit.js` — posted speed limits from OSM `maxspeed` tags via Overpass (free tier: one ~60 m query at most every 12 s, none while the bike stays on the matched way; heading-aligned matching so a crossing road never wins). Ride Mode renders it as a MUTCD sign, hidden when the road carries no tag.
- `src/engine/splits.js` — break-point recommendations for loops and long days.
- `src/engine/exporters.js` — GPX (waypoint names carry planned ETAs — keep that; riders use it for schedule checks) and ICS (assumes UTC-6/Mountain Time — known limitation).
- `src/engine/geocode.js` — Nominatim search (free tier: keep request volume debounced/low).
- `src/engine/stream.js` — `readPlannerStream(res, onLine)` reads the functions' NDJSON.

## AI planner functions

Shared model logic lives in `netlify/lib/planner-core.mjs` (`runChat`, `runGenerate`, budgets). Three transports:

- `netlify/functions/chat.mjs` — streams NDJSON (`{type: start|delta|building|beat|done|error, ms}`). The host severs streams at ~58s; heartbeats every 2s keep bytes flowing. **Never convert these functions to plain buffered JSON responses — Netlify kills synchronous functions at 10s.**
- `netlify/functions/planner-background.mjs` — Netlify *background* function (the `-background` suffix is load-bearing): 15-minute ceiling, answers 202, reports progress into Netlify Blobs store `planner-jobs` (~1 write/sec coalesced).
- `netlify/functions/planner-status.mjs` — poll endpoint for background jobs; emits the same event shapes as the stream so the client reads either transport identically.

Model: `claude-sonnet-5` (deliberate cost choice — don't upgrade without asking). Chat mode returns text + a `propose_trip_changes` tool call (ops + `saveAs`/`overwriteScenarioId` for scenario writes); generate mode (`mode:'generate'`) returns a full trip via the `generate_trip` tool, which the client re-ids and date-cascades in `NewTripModal`. The client sends digests (`tripDigest` + `feasibilityDigest` + `splitsDigest`) plus full trip JSON and the scenario list — keep digests in sync with engine changes so the AI reasons from real numbers.

## Accounts + library backup (Aug 15, 2026)

The one failure the app could not survive: localStorage is the device's truth, so deleting the PWA deleted the roadbook. An account gives the library a second home.

- **`src/engine/auth.js`** — email + password (`signUp`/`signIn`/`sendReset`/`updatePassword`, `useAuth()`). Deliberately a different credential from the join code: the code opens a TRIP for a crew standing in the same car park, an account opens a LIBRARY on a new phone a year later. A device that already carries an anonymous session (it joined a shared trip before it had an account) is **upgraded**, not replaced — first `updateUser({email})`, then the confirmation link returns to Roadbook to set a password. Signing up fresh would mint a second user id and strand that rider's trip memberships and authored ops. This flow requires Auth → Providers → **Allow manual linking**.
- **`src/components/Landing.jsx`** — the front door when signed out. A **SOFT gate**: the pitch argues for the account, the card takes the signup, and "Continue without an account" is always there (sticky in `moto.guest.v1`, cleared by signing in so a later sign-out lands back on the door). The whole engine is offline-first and a login wall would trade that away — a rider on day four with no bars still opens their roadbook. Grid areas reorder it on a phone: pitch → card → the four detail points.
- **`src/engine/cloudLibrary.js`** + `user_trips` (schema.sql) — one row per trip in the rider's library. **Not** the op-log sync in `useTripSync.js`: that converges a CREW on one shared trip in realtime; this is one rider's private shelf, so it is last-write-wins per record on `updatedAt`, never a merge of histories. Order at sign-in is **pull → merge → push**; pushing first on a fresh install would upload an empty library over a real one, which is the exact loss this prevents. `planMerge` is pure. A **pristine seed** library (`rec.seeded`, cleared by the first edit) is dropped rather than uploaded, so signing in on a new phone restores YOUR trips instead of adding another copy of the Sturgis template. A trip edited AFTER a delete on another device beats the tombstone.
- **Gotcha the tests caught:** the reducer writes edits INTO the existing library record (`syncTrip` mutates + persists), so `state.lib` keeps its identity and an effect watching it alone never fires. The backup effect watches `[state.lib, state.trip, state.scenarios, state.chat]`.
- `supabase.js` reads `import.meta.env ?? {}` so the engine imports under plain node for the check scripts.
- Verified: `scripts/account-check.mjs` (25/25 — restore, merge, tombstones, reducer) plus a browser sim on the BUILT app with a mocked Supabase (41/41: gate, layout at 1280/375/320 incl. 44pt fields, guest stickiness, form switching, sign-in restoring two cloud trips, an edit reaching the account, Settings, sign-out, bad-password copy) and an unconfigured build (5/5 — no gate, no account section, no errors).
- **Backend applied Sep 6, 2026:** `supabase/migrations/20260906134822_account_library_backup.sql` creates `user_trips`; `20260906135252_tighten_account_library_grants.sql` limits it to CRUD for authenticated, non-anonymous owners; `20260906143000_restrict_collab_helpers.sql` prevents the unauthenticated API role from calling the two collaboration SECURITY DEFINER helpers (anonymous riders have sessions and use `authenticated`). RLS checks both `auth.uid()` and the JWT's `is_anonymous` claim. **Confirm email stays on** by owner choice, and the UI completes password setup after the confirmation link. Supabase's built-in sender is low-volume, so configure custom SMTP before a broad rollout.

## Trip sync (Supabase)

Shared trips sync through **the op log, not the trip document** — every mutation is already an op, so riders append theirs and replay each other's through the same `applyOps`. `src/engine/supabase.js` (client, auth, publish/join), `src/engine/useTripSync.js` (persisted outbox out, realtime in), `src/components/SyncPanel.jsx` (in Settings), `supabase/schema.sql` (tables, RLS, `join_trip()`).

- **Shared-trip access still has one no-email door.** Everyone — organiser included — types a name and either shares or joins with a code; the anonymous session is created silently on that first action. Accounts are optional and protect the whole private library, while **the join code remains the shared-trip credential**. This keeps a seven-rider group from depending on confirmation-email delivery in the car park.
- Offline-first is preserved, not bolted around: localStorage stays the device's truth, the outbox persists and drains on reconnect. With no env vars `SYNC_ENABLED` is false and the app behaves exactly as before.
- **Self-healing (Aug 10, 2026):** after every successful drain the pusher calls `compact()` (owner-only by RLS — a rider's call no-ops), folding current state into the server snapshot. Catch-up adopts the snapshot wholesale (then replays newer ops) whenever the device's seq is behind `snapshot_seq` and its outbox is empty — this is the repair path for replicas that forked under the old non-deterministic-id bug: one edit on the owner's phone re-folds truth, and stale devices snap to it on next app open. A rider whose app was OPEN when the fold happened advances seq past it via realtime and won't auto-adopt — "Leave this trip" + rejoin with the code is the manual heal (the join path always adopts).
- **Remote ops do not push onto the undo stack** — undo restores a whole-trip snapshot and would silently revert a co-rider's edit. Conflicting simultaneous edits are last-write-wins by server `seq`, not merged.
- Verified live: two anonymous riders, publish, join by code, ops both directions, realtime in 472ms, roster, and a signed-in stranger seeing 0 trips and 0 ops.
- Keys are `VITE_SUPABASE_URL` / `VITE_SUPABASE_KEY` (publishable — safe in the client, RLS is the lock). The Netlify project lives on Niall's account, so env vars there are his to set.

## Conventions & gotchas

- Design system: Roadbook is a **precision touring instrument** — part field atlas, part low-glare cockpit. Dark and light are independently authored palettes in `src/styles/app.css`, not inversions: warm bone on blue-black metal at night, mineral paper and carbon ink by day. Signal orange is reserved for primary action/attention; turquoise identifies route intelligence and live state. Barlow carries interface hierarchy, Barlow Condensed the wordmark/editorial display, and IBM Plex Mono only dates, measurements, route IDs, and machine state. Durable rules and QA widths live in `DESIGN.md`. Phase colors still come from `PHASES` in `seedTrip.js`; on the light basemap MapView substitutes `LIGHT_SAFE` colors.
- `MapView` re-registers nothing on style switch: layers are re-added by `scheduleDraw` via `drawAllRef` (a ref to the latest closure — React StrictMode double-mounts the map, and init-time handlers would otherwise capture stale state). Keep new map event handlers going through refs.
- Mobile: `src/hooks/useMediaQuery.js` drives a tabbed one-pane layout; the map lives in a hidden tab and relies on the ResizeObserver in MapView to `resize()` when shown.
- Waypoints: `kind` ∈ start/via/fuel/photo/end, `fuel: true` drives fuel-gap math, `dwell` minutes override `DWELL_DEFAULT`. `mile` is legacy field-guide mileage — null it when coordinates change (`update_waypoint` from the location editor already does).
- Chat history persists per trip on the library record (`rec.chat`, capped 60 messages) — ChatPanel hydrates on trip switch and dispatches `save_chat`.
- `src/components/RideMode.jsx` — GPS HUD: projects `watchPosition` fixes onto the day's waypoint legs (`planPosition`), delta vs plan = clock − planned-minutes-at-position; wake-lock held while open. PWA manifest in `public/`.
- localStorage keys: `moto.trips.v1` (library), `moto.budget.v1`, `sturgis.routeCache.v5` (Valhalla planning keyed by route preference, with OSRM fallback), `moto.stepsCache.v6` (Valhalla-first nav steps keyed by route preference), `moto.roadCache.v1` (route refs for map shields), `sturgis.conditions.v1` (weather). Older route/steps cache generations are PURGED on module load (routing.js) — leaving them orphaned stacked multi-MB dead weight until localStorage hit quota, saves of the current cache failed, and the app re-routed the whole trip on every launch. Cached geometry is rounded to 5 decimals for the same reason. Legacy `sturgis.trip.v2`/`sturgis.scenarios.v1` migrate on first load — don't remove the migration until well after Aug 2026.
- The seed Sturgis trip (`src/data/seedTrip.js`, now titled "Sturgis Trip Template") doubles as the "template" option in NewTripModal and the Reset target; `earlyExitTemplate.js` is the second built-in. Both snap to `seedPlaces.js` / `earlyExitPlaces.js` at load — regenerate with `node tools/verify-seed.mjs --write` (and `--trip early-exit --write`) after editing either. Its documented mileage is known-low vs routed reality (e.g. Missoula→Bozeman is ~203 mi, not 110) — the engine's routed numbers are the truth.
